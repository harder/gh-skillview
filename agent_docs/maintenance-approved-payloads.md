# Approved immutable payloads

`ApprovedPayloadStore` retains native byte/metadata archives separately from
ordinary replacement plans. Every attempt has one private GUID directory before
capture. Completed, incomplete and unreferenced directories each reserve the
entire fixed working bound; four captures exhaust admission. Each reservation
covers three bounded payload/manifest archives plus the bounded approval header.
No retry, plan cleanup or policy edit silently deletes evidence or frees quota.
Unknown/malformed namespace entries refuse. Read-only inventory projects bounded
completed headers, with partial evidence explicitly reported; publishing intent
and restoration always reopen and verify every referenced archive byte and native
metadata recipe under the retained native store authority.

Custom capture retains actual installed I, including authored bytes, extras,
deletions relative to any external source, modes and supported metadata. It has
no fabricated B/C, commit, pristine baseline or provider result. Recorded local
paths/remote tracking remain recorded provenance. A remote-verified capture
requires the exact completed selected plan and its actually installed candidate,
with current native payload and owner authority, immutable raw Git archive and
actual provider output. Preparing a plan or presenting matching SKILL tracking is
insufficient. Provider/source evidence is copied into the independent archive;
the executable and original source need not remain available after capture.

The completed header binds archive manifest/fingerprint, actual native evidence,
full metadata coverage/recipes, complete authored/tracking metadata, original
source/owner namespace, installation and process-context digest. It stores no
environment credentials. Owned captures additionally retain the actual held
registry file/parent native identities and exact raw selected entry/fingerprint.
That historical observation is provenance; restore prepares a fresh supported
owner transition rather than replaying captured owner bytes as write authority.
Unknown metadata can remain partial diagnostic evidence
but cannot produce a completed approval. It never upgrades CAP_SYS_ADMIN refusal
or unknown Windows/macOS metadata into preservation authority.

Capturing and setting policy are separate operations. Setting approved-immutable
requires explicit consent, the independently supplied exact capture fingerprint,
the current desired-policy fingerprint and a held verified local capture with
matching source/subject/context. Direct policy writes refuse unverified approval
IDs. Changing intent never edits an actual pin. Native managers and unsupported
owner/source transitions refuse rather than being adopted by the approval store.

Schema8 `restore-approved` plans copy their evidence into the operation and
materialize exactly those archived bytes and supported metadata through existing
native materializers. They contain `Approval`, omitted from older schema JSON;
they contain no Revision or recorded-base. Current installed I is separately
captured and retained for exact native undo. Supported existing shared gh owner
transitions use the real tree/pin/timestamp editor, preserve current extensions,
keep source/subpath/name fixed and hold the same DATA FILE object. An actual pin
cannot disappear implicitly. Other owner or new-topology transitions have no
authority here.

First Apply and first Recover require exact approval and desired-policy receipts
plus the independently reviewed saved plan/disposition. Already-started recovery
and undo consume copied operation evidence, preserving their existing authority
if the approval store, provider or original source later becomes unavailable.
Full authored bytes and metadata are rechecked from the retained archive, never
re-resolved through a mutable tag or local source. Native originals are retained;
disk verification does not observe or update agent sessions.

Lock order is desired-policy writer, approval root/capture, replacement root and
operation, registry DATA FILE, then native payload authorities. Capture-only
operations do not consume replacement-plan quota. No application cancellation or
arbitrary callback is invoked under an ownership lock.

Historical stage2b on actual69 lacked the independently reviewed M19 source-review subsystem.
Every new header therefore carries a required SourceReviewContract identifying
the schema8 integration obligation. Final actual-base integration must require
that real independent acknowledgement receipt before schema8 first native intent
or publication. Schema8 has no historical producer and must never use an absent
optional-field/receipt compatibility fallback. This marker is not an implemented
source-review receipt or source-authenticity verdict.

The original internal boundary did not claim public CLI/UI approval routing.
The private integration adds existing-target consumers and the actual mandatory
source gate; see `maintenance-approved-existing-target.md`. Portable
sets/profiles, fresh native payload/exposure publication and full M17 completion
remain required stages. Native positives must run on a host admitted by the
existing complete-metadata authority; local explicit skips do not prove restore,
receipt deletion, exact undo or supported-provider behavior.

Before acceptance, an admitted native proof lane must execute (without metadata
skips) `ApprovedPayloadStoreTests` and the
`SelectedRevisionPlanTests.ApprovedSelectedArchiveRestoresSameVersionCustomBodyAndExactNativeUndoWithoutProvider`
cases. These must reach actual schema8 Open/Apply/Recover with custom and selected
archives, exact ownerless/shared-pinned evidence, the provider absent, a changed
body with unchanged authored version, and exact undo after the approval store is
unavailable. The schema8 archive-directory whitelist must remain conditioned on
the matching approval/selected fields; the four same names still refuse in
legacy plans. Supported Windows/macOS native proof remains distinct from the
POSIX injected-provider fixture. Never counterfeit complete metadata to reach
these paths on an unadmitted host.
